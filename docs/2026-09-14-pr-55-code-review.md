## P1. Архивируется промпт, который продолжает использовать старая версия теста

Beads: `ait-3cu`

### Где

- `server/src/analysis-prompts/analysis-prompts.service.ts:471`
- `server/src/tests/topics/topics.service.ts:676`
- `server/src/tests/public-links/public-link-access.ts:37`
- `server/src/tests/analysis/analysis.service.ts:422`

### Проблема

Перед архивацией промпта `deletePrompt()` проверяет только `activePublishedVersion` и
`activeDraftVersion` теста. Исторические версии теста в эту выборку не входят.

При публикации следующей версии теста предыдущая версия переводится в `ARCHIVED`, однако публичные
ссылки специально остаются привязанными к своей версии. Проверка доступности публичной ссылки
запрещает только `DRAFT`, поэтому ссылка на `ARCHIVED`-версию продолжает работать. Фоновый анализ
затем загружает привязанный `analysisPromptVersion` без проверки `prompt.archivedAt`.

В результате промпт можно архивировать, хотя он продолжает использоваться реальным публичным
прохождением.

### Сценарий воспроизведения

1. Опубликовать версию теста V1 с промптом P1.
2. Создать публичную ссылку на V1.
3. Опубликовать V2, использующую другой промпт или не использующую промпт.
4. V1 станет `ARCHIVED`, но публичная ссылка останется доступной.
5. Архивировать P1 через админку — сервер разрешит операцию.
6. Пройти тест по старой ссылке — анализ по-прежнему использует архивированный P1.

### Рекомендация

При архивации искать все версии тестов, которые используют версии промпта и при этом имеют
действующие публичные ссылки или незавершённые/релевантные попытки. Альтернатива — формально
запретить использование архивированного промпта в анализе, но тогда потребуется корректно закрыть
или мигрировать связанные ссылки и попытки.

Обязательно добавить интеграционный тест с цепочкой `V1 → ссылка → публикация V2 → архивирование
промпта V1`.

## P1. Невалидная дата в `RuDateInput` позволяет сохранить старое значение

Beads: `ait-hw7`

### Где

- `client/src/shared/ui/ru-date-input.tsx:56`
- `client/src/shared/ui/ru-date-input.tsx:81`
- `client/src/widgets/admin-settings-workspace/ui/admin-settings-workspace.tsx:69`
- `client/src/widgets/admin-settings-workspace/ui/admin-settings-workspace.tsx:94`

### Проблема

Неполный или несуществующий ввод хранится только во внутреннем `draft` компонента. Пока значение не
станет валидным, `onChange` родителя не вызывается. Поэтому родитель продолжает хранить предыдущую
валидную ISO-дату и оставляет кнопку сохранения активной.

Пользователь видит в поле невалидную дату, но при сохранении на сервер отправляется старая дата.
Это особенно опасно для даты публикации политики персональных данных: интерфейс визуально обещает
одно значение, а сохраняет другое.

### Сценарий воспроизведения

1. Открыть настройки политики с уже сохранённой датой.
2. Изменить дату на неполную, например удалить последнюю цифру года, либо ввести `31.02.2026`.
3. Поле показывает новый неполный/невалидный текст.
4. Кнопка «Сохранить политику» остаётся активной, поскольку форма всё ещё содержит прежний ISO.
5. Нажать сохранить — отправится прежняя дата, а не показанная пользователю.

### Рекомендация

Передавать наружу отдельное состояние валидности/черновика либо сообщать родителю `null` при любом
неполном или невалидном вводе. Форма должна блокировать submit, пока отображаемое значение нельзя
однозначно преобразовать в ISO.

Добавить тест уровня формы: начать с валидной даты, сделать значение невалидным и убедиться, что
submit заблокирован и mutation не вызывается.

## P1. Изменение сущности и запись аудита выполняются неатомарно

Beads: `ait-wlf`

### Где

- `server/src/admin/admin.service.ts:248`
- `server/src/admin/admin.service.ts:258`
- `server/src/analysis-prompts/analysis-prompts.service.ts:387`
- `server/src/tests/public-links/public-link.service.ts:299`
- `server/src/app-settings/privacy-policy-settings.service.ts:168`

### Проблема

Основная мутация и `auditService.record()` выполняются отдельными запросами к базе. Если запись
аудита падает после успешной мутации, API отвечает ошибкой, хотя данные уже изменены.

Для создания пользователя это даёт особенно неприятный результат: пользователь создан, клиент
получил ошибку, а повторная попытка завершается конфликтом `Email already exists`. При этом событие
`USER_CREATED` отсутствует. Аналогичный разрыв возможен для ролей, паролей, промптов, настроек и
публичных ссылок.

Такой журнал нельзя считать полным, а клиент не может безопасно повторять запрос после ошибки.

### Сценарий воспроизведения

1. Замокать или искусственно вызвать ошибку `auditEvent.create`.
2. Выполнить создание пользователя либо изменение публичной ссылки.
3. Запрос вернёт ошибку.
4. Проверить базу: основная сущность уже создана/изменена, audit event отсутствует.

### Рекомендация

Выполнять бизнес-мутацию и запись события в одной Prisma-транзакции. `AuditService` может принимать
transaction client либо предоставлять метод, работающий с переданным `Prisma.TransactionClient`.

Добавить negative-path тест: ошибка аудита должна откатывать основную мутацию.

## P2. Истечение попытки зависит от часов устройства ученика

Beads: `ait-60b`

### Где

- `client/src/widgets/public-test-workspace/ui/public-test-run-workspace.tsx:76`
- `client/src/widgets/public-test-workspace/ui/use-public-test-run-countdown.ts:8`
- `client/src/widgets/public-test-workspace/ui/use-public-test-run-countdown.ts:16`
- `server/src/tests/session/attempt.guards.ts:13`

### Проблема

Клиент скрывает вопросы, когда countdown, рассчитанный через браузерный `Date.now()`, достигает
нуля. Сервер разрешает или запрещает ответы по собственному времени.

Если часы устройства ученика спешат, UI преждевременно показывает финальный экран истечения, хотя
сервер всё ещё считает попытку активной и готов принимать ответы. Перезагрузка не помогает, пока
сохраняется рассинхронизация часов.

### Рекомендация

Передавать серверное время вместе с сессией и вычислять поправку clock skew либо использовать
клиентский countdown только как индикацию, а окончательно закрывать вопросы после
сервер-подтверждённого статуса `EXPIRED`.

Добавить тест с браузерным временем, опережающим серверное.

## P2. Проверка OpenRouter может блокировать настройки до 120 секунд

Beads: `ait-s3y`

### Где

- `server/src/admin/admin-settings.controller.ts:46`
- `server/src/openrouter/openrouter.client.ts:11`
- `server/src/openrouter/openrouter.client.ts:151`
- `server/src/openrouter/openrouter.client.ts:288`

### Проблема

`GET /admin/settings/openrouter` теперь синхронно ожидает `checkHealth()`, который загружает полный
каталог моделей. `fetchModels()` использует общий таймаут OpenRouter — по умолчанию 120 секунд.

При зависшем или фильтруемом сетевом соединении пользователь до двух минут видит «проверяем связь»,
хотя цель health-check — быстро показать состояние интеграции. Также каждый запрос настроек
повторно загружает каталог моделей.

### Рекомендация

Ввести отдельный короткий таймаут для health-check, например 3–10 секунд, и кэшировать результат на
небольшой TTL. Ещё лучше — не связывать получение локальных настроек с доступностью внешнего
провайдера: вернуть настройки сразу, а проверку выполнять отдельным endpoint/query.
