# Подсказки в форме учебного заведения

## Контекст

Форма создания и редактирования учебного заведения уже содержит реквизиты оператора персональных данных, но не объясняет формат значений и визуально не различает обязательные и необязательные поля.

Изменение классифицируется как `existing-feature-change` в модуле `tests`. Prisma, backend API, маршруты и manifest не меняются.

## Цель

Администратор должен с первого просмотра понимать:

- что необходимо для сохранения записи;
- какие поля нужны, чтобы организация стала доступна в режиме обработки ПДн от её имени;
- какие реквизиты можно заполнить позже;
- в каком формате вводить каждое значение.

## Правила обязательности

`Название` — обязательное поле самой формы. Оно получает метку `*` и HTML-атрибут `required`.

Следующие поля получают метку `*`, но не HTML-атрибут `required`, потому что неполную организацию разрешено сохранить:

- `Полное наименование`;
- `Сокращённое наименование`;
- `Политика обработки ПДн`.

Они обязательны только для серверного состояния `personalDataReady` и использования организации как оператора ПДн.

Остальные поля получают видимую пометку `— необязательно`:

- ИНН;
- ОГРН;
- юридический адрес;
- email;
- телефон;
- документ согласия;
- логотип.

Перед группами реквизитов показывается пояснение:

> - — обязательно для обработки ПДн от имени организации. Неполную организацию можно сохранить и заполнить позже.

## Плейсхолдеры

Плейсхолдеры служат только примером формата и не заменяют связанные `label`.

| Поле                     | Пример                                                                           |
| ------------------------ | -------------------------------------------------------------------------------- |
| Название                 | `Например: Лицей № 42`                                                           |
| Полное наименование      | `Например: Муниципальное автономное общеобразовательное учреждение «Лицей № 42»` |
| Сокращённое наименование | `Например: МАОУ «Лицей № 42»`                                                    |
| ИНН                      | `Например: 1234567890`                                                           |
| ОГРН                     | `Например: 1234567890123`                                                        |
| Юридический адрес        | `Например: г. Казань, ул. Школьная, д. 1`                                        |
| Email                    | `Например: office@school.example`                                                |
| Телефон                  | `Например: +7 900 000-00-00`                                                     |
| Политика обработки ПДн   | `https://school.example/privacy`                                                 |
| Документ согласия        | `https://school.example/consent`                                                 |
| Логотип                  | `https://school.example/logo.svg`                                                |

## Компоненты

Изменение остаётся внутри существующего workspace:

- `education-organization-operator-fields.tsx` хранит конфигурацию labels, обязательности и примеров для десяти операторских полей;
- `education-organizations-create-card.tsx` и `education-organizations-edit-card.tsx` продолжают переиспользовать один компонент;
- `Название` получает одинаковую маркировку обязательности в create и edit cards;
- существующие readiness badges и серверная формула `personalDataReady` не меняются.

Новые abstractions, страницы, зависимости и CSS-токены не требуются.

## Доступность

- Каждый input сохраняет связанный `label` и уникальный `id`.
- Обязательность не кодируется только цветом: `*` сопровождается текстовым пояснением.
- Только реально обязательное для submit поле `Название` получает `required`.
- Операторские поля не получают ложный `required`, чтобы не блокировать поэтапное заполнение.
- Placeholder не используется вместо label.

## Проверка

Тесты create/edit cards должны подтверждать:

- `Название *` и HTML `required`;
- три operator-ready label со звёздочкой без HTML `required`;
- пометку `— необязательно` у остальных полей;
- пояснение о поэтапном заполнении;
- предметные placeholders в create и edit формах;
- сохранение существующих fieldset/legend и readiness badges.

После изменения файлов `client/` необходимо пересобрать frontend-контейнер, затем запустить целевые Vitest, client build, ESLint, Prettier и `git diff --check`.
