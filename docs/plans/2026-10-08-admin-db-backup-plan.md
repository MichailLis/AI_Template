## Что подтвердилось

- Прод: `postgres:16-alpine`, backend из `server/Dockerfile` (runtime `node:24.21.0-bookworm`, пользователь `node`), один том `postgres_data`. Бэкап сейчас только ручной (`docs/deployment-dockerhub.md`, раздел 8).
- В bookworm `postgresql-client` версии 15, а `pg_dump` 15 откажется работать с сервером 16. Нужен клиент 16 из репозитория PGDG.
- `POSTGRES_USER` в официальном образе суперпользователь, поэтому создание и переименование БД доступны.
- `client_max_body_size 10m` в `client/nginx/default.conf`.
- `multer` уже приходит с `@nestjs/platform-express`, загрузок файлов в коде пока нет.
- При старте backend `AnalysisService.onApplicationBootstrap` подбирает зависшие LLM-анализы, а entrypoint выполняет `prisma migrate deploy`. Поэтому перезапуск после restore безопасен, а дамп со старой схемой догоняется миграциями.
- Локальный compose использует `prisma:push`, таблицы `_prisma_migrations` там может не быть.

## Решения по умолчанию

| Вопрос            | Решение                                                                                                                                                                                                                                                                                                                                                              |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Как делается дамп | `pg_dump -Fc --no-owner --no-acl` всей БД (не `-n public`, иначе потеряется `CREATE EXTENSION citext`), `spawn` без shell, таймаут с убийством процесса. Пишется во временный файл, после успеха sha256 и переименование. Перед стартом проверка свободного места                                                                                                    |
| Версии            | При старте модуль сравнивает `pg_dump --version` с `SHOW server_version`; при несовпадении мажора бэкапы недоступны с понятной ошибкой в админке                                                                                                                                                                                                                     |
| Хранение          | Том `ai_template_backups` → `/backups` (каталог создаётся в образе с владельцем `node`, Docker перенесёт права в пустой том)                                                                                                                                                                                                                                         |
| Срок              | 14 дней и не более 30 копий; последняя успешная, импортированные до использования и `PRE_RESTORE` за последние 7 дней не удаляются                                                                                                                                                                                                                                   |
| Ручной запуск     | «Создать копию» и «Создать и скачать». Одна операция за раз: бэкап, импорт и restore взаимно исключают друг друга (замок в памяти, контейнер один)                                                                                                                                                                                                                   |
| Расписание        | Включено, раз в сутки в 03:00 UTC, меняется в админке. Пропуск, если успешная копия за последние 20 ч уже есть                                                                                                                                                                                                                                                       |
| Экспорт           | `POST /admin/backups/:id/download-link` выдаёт одноразовую ссылку на 60 с, `GET /admin/backups/download/:token` стримит файл. Токен одноразовый, поэтому попадание в access-лог nginx безопасно                                                                                                                                                                      |
| Импорт            | `POST /admin/backups/import`, multipart в `diskStorage` во временный каталог, лимит `BACKUP_MAX_UPLOAD_MB` (500). Проверки: сигнатура `PGDMP`, `pg_restore --list`, затем полная проверка во временной БД (ниже). После проверки файл становится копией `IMPORTED`                                                                                                   |
| Восстановление    | См. следующий раздел. Одинаково для своих копий и импортированных                                                                                                                                                                                                                                                                                                    |
| Аудит             | `AuditEntityType.DATABASE_BACKUP` (миграция), действия `BACKUP_CREATED`, `BACKUP_FAILED`, `BACKUP_DOWNLOADED`, `BACKUP_DELETED`, `BACKUP_IMPORTED`, `BACKUP_RESTORED`, `BACKUP_SETTINGS_UPDATED`. Запись о restore пишется после перезапуска, в восстановленную БД, а копия этого же события лежит в `/backups/audit.log`, чтобы не потеряться при следующем restore |

## Как устроено восстановление

1. Админ выбирает копию и вводит `RESTORE`. Создаётся копия `PRE_RESTORE` текущей БД.
2. Backend включает режим обслуживания: на всё, кроме статуса операции, отвечает 503.
3. `pg_restore --no-owner --no-acl` во временную БД `<db>_restore`.
4. Проверки во временной БД: есть `users` и хотя бы один активный ADMIN; последняя миграция из `_prisma_migrations` не новее последней миграции в образе (более старая допустима, её догонит `migrate deploy`). Если `_prisma_migrations` нет (локальный `prisma:push`), restore разрешён только в dev с предупреждением.
5. При ошибке временная БД удаляется, рабочая не тронута.
6. Подмена через служебную БД `postgres`: закрыть соединения к рабочей (`pg_terminate_backend`), `ALTER DATABASE <db> RENAME TO <db>_before_<время>`, `ALTER DATABASE <db>_restore RENAME TO <db>`. Прежняя БД хранится до следующего restore и удаляется кнопкой или следующим restore.
7. Очистить `hashedRefreshToken` у всех, записать время restore в `/backups/state.json`; `AccessTokenStrategy` отклоняет токены с `iat` раньше этого времени.
8. Backend завершает процесс; Docker перезапускает его, entrypoint применяет миграции. Админ входит заново.

Откат: вернуть прежнюю БД обратным переименованием (кнопка «Отменить последнее восстановление» пока прежняя БД существует) или восстановить `PRE_RESTORE`.

Риски, которые остаются:

- Импортированный дамп может содержать любой SQL (функции, триггеры) и выполняется с правами суперпользователя. Импорт только для ADMIN, предупреждение в подтверждении.
- Подмена удваивает место на диске на время restore. Перед стартом проверяется свободное место.
- Данные, записанные между `PRE_RESTORE` и подменой, теряются: режим обслуживания закрывает это окно.

## Изменения по слоям

1. `schema.prisma`: только новое значение `AuditEntityType`; `prisma:generate`, миграция.
2. Backend `server/src/backups`: сервис дампа и восстановления, планировщик, хранилище метаданных в томе, фоновые задачи со статусом, контроллер с `@ApiOperation` и типизированным `@ApiResponse`, DTO с датами строкой и без путей к файлам, ошибки в формате `{ success:false, error:{code,message} }`. Middleware режима обслуживания и проверка `iat` в `AccessTokenStrategy`. Запись в `template/features.manifest.json`.
3. `npm run gen:api`, затем вкладка «Резервные копии» в `widgets/admin-settings-workspace`: список, статусы, создать, скачать, удалить, импорт, восстановить, отменить восстановление, расписание и срок хранения, прогресс фоновой операции.
4. Docker и прод:
   - `server/Dockerfile`: `postgresql-client-16` из PGDG, `mkdir /backups` с владельцем `node`.
   - `docker-compose.deploy.yml`: том `${BACKUPS_VOLUME_NAME:-ai_template_backups}:/backups`, переменные `BACKUP_DIR`, `BACKUP_MAX_UPLOAD_MB`.
   - `docker-compose.yml` (dev): backend на голом `node`-образе без `pg_dump`. По умолчанию добавить установку клиента 16 в команду запуска или отдельный dev-образ; без клиента вкладка показывает «недоступно».
   - `client/nginx/default.conf`: для `/api/admin/backups/` поднять `client_max_body_size` до лимита, отключить буферизацию запроса и ответа, `proxy_read_timeout 300s`.
   - `.env.deploy.example`, `docs/deployment-dockerhub.md`, `docs/server-admin-deploy.md`, `RESTORE.md`: раздел про бэкапы, том `/backups` нужно копировать с сервера вместе с остальным.
   - Пересобрать и опубликовать образы backend и frontend.
5. Тесты: unit на сервис (мок `spawn`, разбор `DATABASE_URL`, ротация, взаимоисключение, отклонение импорта без ADMIN и с новой схемой, проверка `iat`); интеграционный «dump → импорт → restore → подмена» на docker-postgres по образцу `verify-prisma-migrations`; тест вкладки. Гейты `verify:local`, `verify:template`.
