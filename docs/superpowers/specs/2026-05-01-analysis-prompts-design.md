# Analysis Prompts Design

Date: 2026-05-01
Branch: `codex/analysis-prompts`

## Goal

Build a versioned prompt system for analyzing student test answers.

The system must let an admin create and test analysis prompts, publish prompt versions,
attach one published prompt version to a test topic version, run student analysis
asynchronously after test completion, show a formatted result to the student, and keep the
same result available for admins in attempt statistics.

## Decisions Confirmed

- Prompt attachment belongs to a test topic version, not to the topic as a whole.
- One test topic version can have only one active analysis prompt version.
- Prompt versions are required.
- Prompt testing happens in the prompt constructor, not inside the test editor.
- Prompt testing uses all questions from a selected test source.
- The test source in Prompt Studio is only a helper for simulation. It is not a permanent
  prompt-to-test binding.
- Test answers for prompt testing should be generated by AI from the selected questions.
- Student analysis runs asynchronously after completion.
- The student sees a formatted result page based on structured JSON.
- Admins can later view the same stored analysis result on the attempt detail screen.

## Current Project Fit

The repository already has the right foundations:

- Prompt Studio route: `/admin/prompts`
- Tests editor route: `/admin/tests`
- Public student result route: `/t/:code/result/:sessionToken`
- OpenRouter calls already go through backend-only proxy endpoints.
- Student attempts already have `TestStudentAnalysis`.
- Current analysis is a deterministic `STUB` created on finish.
- Public result and admin attempt detail already expose analysis status and payload fields.

The implementation should extend these surfaces instead of creating a parallel AI subsystem.

## Reuse And Simplicity Guardrails

Implementation must follow `CLAUDE.md` and `AI_GUIDE.md`.

Assumptions to keep explicit:

- The feature is an extension of the existing tests, prompt, public result, and admin stats
  surfaces.
- Prompt simulation in Prompt Studio is a testing tool only.
- The first implementation should optimize for correctness and maintainability, not for a
  speculative prompt marketplace or workflow engine.

Reuse existing project pieces wherever possible:

- Use the existing OpenRouter backend proxy and helpers instead of adding direct frontend
  OpenRouter calls.
- Extend the current prompt workspace instead of creating a second prompt UI.
- Extend `TestStudentAnalysis` instead of creating a parallel result table.
- Extend the existing public result and admin attempt detail screens instead of adding new routes.
- Use existing generated API hooks, shadcn UI primitives, FSD boundaries, DTO style, and Prisma
  service patterns.
- Reuse current test version lifecycle semantics when freezing the selected prompt version.

Avoid speculative work:

- Do not introduce a new queue system unless the repository already has one or verification proves
  in-process deferred execution is not enough for the MVP.
- Do not add multiple prompts per test version.
- Do not make the output schema admin-configurable in the MVP.
- Do not store synthetic simulation runs unless a later requirement needs history.
- Do not refactor unrelated prompt/test/public-link code while adding this feature.

Every changed line in implementation should trace back to one of these requirements.

## Domain Model

Add persisted prompt entities:

- `AnalysisPrompt`
  - id
  - title
  - description
  - archivedAt
  - activeDraftVersionId
  - activePublishedVersionId
  - createdAt
  - updatedAt

- `AnalysisPromptVersion`
  - id
  - promptId
  - versionNumber
  - status: `DRAFT | PUBLISHED | ARCHIVED`
  - promptText
  - model
  - temperature
  - responseSchema
  - createdAt
  - updatedAt

Extend existing test entities:

- `TestTopicVersion`
  - add nullable `analysisPromptVersionId`
  - relation to `AnalysisPromptVersion`

Extend existing analysis storage:

- `TestStudentAnalysis`
  - keep `providerMode`, `status`, `summary`, `rawText`, `errorMessage`, `generatedAt`
  - add nullable `promptVersionId`
  - optionally add `model` if useful for debugging/reproducibility

The `summary` field stores the parsed structured JSON returned by the LLM.
The `rawText` field stores the raw model response for troubleshooting.

## Structured Analysis JSON

Use a fixed schema for the student-facing result, aligned with the product requirement:

```json
{
  "skillsLevel": {
    "title": "string",
    "summary": "string",
    "items": [
      {
        "name": "string",
        "level": "low | medium | high",
        "score": 0,
        "description": "string"
      }
    ]
  },
  "thinkingType": {
    "title": "string",
    "type": "string",
    "description": "string",
    "strengths": ["string"]
  },
  "personalityTraits": {
    "title": "string",
    "traits": [
      {
        "name": "string",
        "description": "string",
        "careerImpact": "string"
      }
    ]
  },
  "careerDevelopment": {
    "summary": "string",
    "recommendedDirections": ["string"],
    "developmentRecommendations": ["string"],
    "professionalNextSteps": ["string"]
  }
}
```

The backend should pass this schema to OpenRouter as:

- `response_format: json_schema`
- `strict: true`
- `provider.require_parameters: true`
- response healing enabled where supported by the existing OpenRouter helper

The prompt text can still be edited by admins, but the output shape should remain fixed so the
student result UI can render reliably.

## Prompt Studio UX

`/admin/prompts` should become a real analysis prompt constructor.

Core areas:

- Prompt list
  - create prompt
  - archive prompt
  - view draft and published versions

- Version editor
  - title/description at prompt level
  - prompt text
  - model selector
  - temperature
  - fixed output schema preview
  - save draft
  - publish prompt version

- Simulation panel
  - choose an existing test as the question source
  - load all questions from the selected draft or published question set
  - treat loaded questions as simulation input only
  - generate test answers with AI
  - run current prompt against `questions + generated answers`
  - show raw JSON
  - show formatted student-result preview
  - show validation errors if JSON does not match the schema

Important wording: Prompt Studio chooses test questions for simulation. It does not attach the
prompt to that test.

## Test Editor UX

In `/admin/tests/:topicId/settings`, add an analysis prompt section.

Behavior:

- show currently attached prompt version for the active draft
- let admin select one published analysis prompt version
- allow clearing the prompt from a draft
- block or warn on publishing a test without an analysis prompt, depending on product preference
- when the test is published, the selected prompt version is frozen into that `TestTopicVersion`

The question editor remains focused on test content.
Prompt editing stays in Prompt Studio.

## Student Analysis Flow

After student finishes a test:

1. Save final answers.
2. Mark attempt as completed.
3. Create or update `TestStudentAnalysis`:
   - `status = PENDING`
   - `providerMode = LLM` if the topic version has a prompt
   - `providerMode = STUB` or `FAILED` fallback if no prompt is configured
4. Start asynchronous analysis execution.
5. Public result endpoint returns the current analysis status.
6. Student result page polls until `READY` or `FAILED`.

When the LLM succeeds:

- parse and validate JSON against the fixed schema
- store parsed JSON in `summary`
- store raw response in `rawText`
- set `status = READY`
- set `generatedAt`

When the LLM fails:

- set `status = FAILED`
- store a safe error message in `errorMessage`
- keep the public message human-friendly

## Student Result UI

The public result screen should render:

- processing state while analysis is pending
- current level of basic skills
- thinking type
- personality traits
- career/professional development summary
- recommendations for self-development
- next steps for career and professional growth
- friendly failure state if analysis cannot be generated

The UI should use the existing public test theme layout and avoid exposing raw enum values.

## Admin Result UI

The admin attempt detail dialog should keep access to:

- analysis status
- prompt version used
- generated timestamp
- formatted analysis view
- raw JSON/debug view
- student answers

This lets admins inspect exactly what the student saw and troubleshoot bad prompt output.

## Implementation Phases

1. Data model and contracts
   - add Prisma models and relations
   - define DTOs and fixed analysis JSON schema
   - regenerate Prisma and API client

2. Prompt management backend
   - CRUD and version lifecycle
   - publish/archive behavior
   - list published prompt versions for test attachment

3. Prompt Studio frontend
   - list/create/edit/publish prompt versions
   - model selection using existing OpenRouter model proxy
   - simulation shell

4. Test question simulation
   - list available test sources
   - pull all questions from selected source
   - generate synthetic student answers through OpenRouter

5. Analysis simulation
   - run prompt against selected questions and generated answers
   - validate returned JSON
   - show raw JSON and formatted preview

6. Test version attachment
   - add prompt selector in test settings
   - persist selected prompt version on the draft
   - preserve selection when publishing version

7. Real student analysis
   - enqueue or defer LLM analysis after finish
   - store status/result/errors in `TestStudentAnalysis`
   - keep polling-compatible public result response

8. Student/admin rendering
   - replace raw JSON result with formatted public blocks
   - add admin formatted/debug views for stored analysis

9. Verification
   - unit tests for DTO/schema validation
   - service tests for prompt version lifecycle
   - service tests for test attachment/publish preservation
   - analysis service tests for success/failure JSON handling
   - frontend build/lint/API generation checks
   - final `npm run verify:local`

## Open Questions

- Should publishing a test without an attached analysis prompt be blocked, or only warned?
- Should analysis automatically retry after OpenRouter failure, or should retry be admin-triggered?
- Should admins be able to re-run analysis for an existing attempt with the same prompt version?
- Should generated synthetic answers be saved as prompt test runs, or remain local/transient for now?

Recommended MVP answers:

- Warn, but do not block publishing without a prompt.
- No automatic retry in MVP; add admin retry later.
- No re-run existing attempts in MVP; add a manual action later.
- Keep synthetic simulation runs transient at first.
