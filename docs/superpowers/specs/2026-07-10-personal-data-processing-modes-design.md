# Режимы обработки персональных данных для публичных тестов

## Контекст и решение

Требование расширяет существующий bounded context `tests`. Новая сущность `Organization`, новые роли и отдельный кабинет учебного заведения не создаются. Термин «организация» на этом этапе означает существующую `EducationOrganization`.

Режим обработки персональных данных и юридический оператор задаются на `TestPublicLink`, потому что одна опубликованная версия теста может использоваться разными публичными ссылками и разными операторами. Поддерживаются два режима:

- `PUBLIC`: оператором является владелец платформы — АНО «Центр развития компьютерного спорта и цифровых технологий»;
- `ON_BEHALF_OF_EDUCATION_ORGANIZATION`: оператором является выбранное активное учебное заведение.

Упоминания ветки `prod` в исходном ТЗ заменяются на `main` по прямому указанию пользователя.

## Границы

- Изменение классифицируется как `existing-feature-change`.
- Владелец backend/frontend-контракта: `tests`.
- Prisma-владельцы: `EducationOrganization`, `TestPublicLink`, `TestStudentAttempt`.
- Затронутые route roots: `/admin/tests/education-organizations`, `/admin/tests/public-links`, `/t/:code`.
- `template/features.manifest.json` не меняется: новый feature, route root и generated API directory не появляются.
- Nest-генератор не запускается: расширяется существующий модуль.
- Новые зависимости не добавляются.

## Модель данных

`EducationOrganization` получает nullable-поля `fullName`, `shortName`, `inn`, `ogrn`, `legalAddress`, `email`, `phone`, `privacyPolicyUrl`, `consentDocumentUrl`, `logoUrl`. Nullable-ограничение сохраняет совместимость со старыми записями; готовность к режиму по поручению проверяется бизнес-валидацией.

`TestPublicLink` получает `personalDataProcessingMode` с default `PUBLIC` и snapshot-поля полного/краткого имени оператора и ссылок на документы. Snapshot создаётся при создании ссылки и явно пересобирается только при изменении режима или учебного заведения. Обычное изменение карточки заведения не меняет опубликованный юридический контекст.

`TestStudentAttempt` получает nullable-связь `operatorEducationOrganizationId` и тот же снимок оператора. Попытка копирует данные из публичной ссылки в момент создания; возобновление существующей попытки не перезаписывает согласие.

## Разрешение оператора

В `tests` добавляется один локальный resolver с типом `ResolvedPersonalDataOperator`. Он принимает режим и optional `educationOrganizationId` и возвращает нормализованный набор данных для snapshot/API.

Для `PUBLIC` используются константы платформы и публичный путь `/privacy`; отдельный документ согласия отсутствует. Для режима по поручению resolver требует активное учебное заведение с `fullName`, `shortName` и `privacyPolicyUrl`, а остальные поля остаются необязательными.

Варианты, которые не используются:

- вычисление данных из текущей карточки при каждом открытии — нарушает неизменность юридического контекста;
- единый JSON snapshot — ухудшает типизацию DTO, миграционную прозрачность и фильтрацию;
- новая таблица `Organization` — прямо исключена ТЗ.

## API

Admin create/update public link принимает `personalDataProcessingMode`. При `PUBLIC` `educationOrganizationId` может продолжать использоваться для фиксации/валидации профиля участника, но не становится оператором. При режиме по поручению `educationOrganizationId` обязателен и указывает оператора.

Admin-ответ публичной ссылки возвращает режим и snapshot оператора. CRUD учебных заведений возвращает новые поля и признак готовности документов, вычисляемый из `fullName`, `shortName`, `privacyPolicyUrl` и `isActive`.

Публичный access API всегда возвращает:

```ts
personalData: {
  processingMode: 'PUBLIC' | 'ON_BEHALF_OF_EDUCATION_ORGANIZATION';
  operatorFullName: string;
  operatorShortName: string | null;
  privacyPolicyUrl: string;
  consentDocumentUrl: string | null;
  logoUrl: string | null;
}
```

Старые ссылки читаются как `PUBLIC`; миграция заполняет режим и PUBLIC snapshot, поэтому fallback нужен только как защитный слой для неконсистентных локальных данных.

## UI

Форма учебного заведения остаётся в существующем разделе и делится на блоки «Основное», «Документы ПДн», «Контакты», «Настройки групп/классов». URL-поля валидируются backend и отображают понятные подсказки. В таблице показывается готовность карточки к тестированию по поручению.

В диалоге создания публичной ссылки появляется секция «Обработка персональных данных» с выбором режима. Выбор оператора показывается и становится обязательным только для режима по поручению. Существующая привязка заведения для анкеты участника сохраняется и не меняет смысл автоматически.

На обоих публичных шаблонах постоянно отображается блок оператора. Чекбокс согласия получает название и ссылки из `personalData`; popup не используется. Блокировка старта без `consentAccepted = true` сохраняется на UI и backend.

## Ошибки и совместимость

- Недоступное, неактивное или юридически незаполненное заведение блокирует сохранение режима по поручению.
- Архивирование заведения не ломает старую ссылку: публичная выдача использует snapshot, а профильные правила группы могут продолжать читаться из существующей связи.
- Существующие ссылки и попытки остаются валидными как `PUBLIC`.
- Аналитика, autosave, finishSession и экспорты не зависят от nullable operator-полей.

## Проверка

TDD покрывает DTO, resolver, создание/обновление ссылки, публичный access payload, создание попытки и UI обоих режимов. После backend-контрактов запускаются Prisma generation, migration verification и OpenAPI/Orval generation. После изменений `client/` frontend-контейнер пересобирается до frontend-тестов. Финальные ворота: targeted tests, lint, server/client builds, architecture/maintainability и полный `verify:template` либо явное описание внешнего блокера.
